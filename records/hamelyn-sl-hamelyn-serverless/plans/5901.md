# Coding Plan for hamelyn-sl/hamelyn-serverless#5901: marketplace-crons: Fnac devuelve 500 en pedidos y batch

Source report: [records/hamelyn-sl-hamelyn-serverless/items/5901.md](records/hamelyn-sl-hamelyn-serverless/items/5901.md)

## Summary

La incidencia sigue siendo necesaria, pero el problema restante es más estrecho que el título: los pedidos se vuelven a consultar en el siguiente tick y las retiradas con 5xx ya se recuperan de forma diferida mediante `retryPolicy: TRANSIENT`; en cambio, un 5xx al consultar un batch convierte sus stocks a `SYNC_ERROR/BATCHING` y el cron Fnac no ejecuta la recuperación que podría volver a procesarlos. La evidencia de 288/288 ejecuciones HTTP 200 recogida en https://github.com/Hamelyn-SL/hamelyn-serverless/pull/7214 es positiva, pero ese PR solo reactivó precios y dejó los recoveries fuera de alcance.

## Plan

Corrige la issue https://github.com/Hamelyn-SL/hamelyn-serverless/issues/5901 en un PR enfocado. En `packages/core/src/domain/marketplaces/marketplace.batch.ts`, evita que un error de polling clasificado como `RetryPolicy.TRANSIENT` cambie los stocks del `batchId` a `SYNC_ERROR/BATCHING`; deben conservar `BATCH` para que el siguiente tick los consulte otra vez, generalizando de forma segura el tratamiento actual de 429. Mantén la persistencia de `SYNC_ERROR` para errores funcionales, permanentes o no clasificados y añade cobertura de regresión para ambos caminos. Usa el clasificador compartido, no una lista Fnac duplicada. No añadas retry ciego a `offers_update`/`orders_update`, no actives globalmente los recoveries Fnac, no mezcles la semántica `Product not found` de https://github.com/Hamelyn-SL/hamelyn-serverless/issues/7328 ni el HTTP 400 de envío de https://github.com/Hamelyn-SL/hamelyn-serverless/issues/5618, y no actualices changelog salvo que una convención específica del paquete lo exija. Valida test dirigido, lint y typecheck de `@hamelyn/core`.
