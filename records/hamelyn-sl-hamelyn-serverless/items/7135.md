- `impact:security`: El reporte trata de un límite de confianza servidor-cliente: el backend puede persistir un importe de descuento enviado por el cliente para varios tipos de cupón.

## Summary

Mantener abierto: el `dev` actual sigue persistiendo primero el `appliedDiscount` enviado por el cliente y solo lo sustituye cuando `couponValidation.unitsGranted` existe; https://github.com/Hamelyn-SL/hamelyn-serverless/pull/7157 es la PR de cierre abierta para este arreglo y el issue debe seguir emparejado con ella hasta que se fusione o se sustituya.

## What This Changes

El issue pide que el checkout recalcule y persista el descuento validado por servidor para todos los tipos de cupón, no solo para `FREE_UNITS`.

## Best Possible Solution

Revisar y fusionar https://github.com/Hamelyn-SL/hamelyn-serverless/pull/7157, o un arreglo equivalente y acotado, para que el checkout persista siempre `couponValidation.discount` validado por servidor y solo guarde `unitsGranted` cuando la validación lo devuelva.

## Maintainer Decision

Required: false

## Reproduction Assessment

Sí. Por inspección del código fuente: el checkout copia `checkoutNewOrder.appliedDiscount` y solo lo sobrescribe cuando existe `couponValidation.unitsGranted`, mientras `isCouponValid` ya devuelve `discount` para los demás tipos de cupón sin `unitsGranted`.

## Solution Assessment

Sí. La vía más mantenible es el arreglo acotado de checkout que usa `couponValidation.discount` para cualquier cupón válido y mantiene `unitsGranted` como metadato opcional de `FREE_UNITS`.
