## Label Justifications

- `P2`: Es un bug de checkout con impacto real en descuentos persistidos, pero ya tiene una PR candidata acotada y no bloquea todo el runtime.
- `impact:security`: La issue trata una frontera de confianza: el backend puede persistir un descuento enviado por el cliente para varios tipos de cupón.

## Summary

Debe seguir abierta: el `dev` actual todavía reconcilia el descuento del checkout solo cuando `couponValidation.unitsGranted` existe, mientras que los cupones no `FREE_UNITS` devuelven `discount` sin `unitsGranted`. Hay una PR candidata abierta y vinculada con sintaxis de cierre, así que el cierre debe esperar a que esa PR se fusione o se descarte.

## What This Changes

La issue pide que checkout recalculé o contraste en servidor el `appliedDiscount` para todos los tipos de cupón, no solo para cupones de unidades gratis.

## Best Possible Solution

Fusionar una corrección acotada que use siempre el `discount` validado en servidor para persistir `appliedDiscount` y ajustar `totalPrice`, conservando `unitsGranted` solo como dato específico de `FREE_UNITS` y validando el flujo de checkout real.

## Maintainer Decision

Required: false

## Reproduction Assessment

Sí, por inspección de código: en `dev`, `route.ts` solo sustituye `appliedDiscount` cuando hay `unitsGranted`, y `validation.utils.ts` devuelve `discount` sin `unitsGranted` para los cupones que no son `FREE_UNITS`. No ejecuté un checkout real porque esta revisión es read-only.

## Solution Assessment

Sí, la dirección de https://github.com/Hamelyn-SL/hamelyn-serverless/pull/7157 es la vía más estrecha: reutilizar el descuento ya recalculado por `isCouponValid` y mantener `unitsGranted` como campo opcional de unidades gratis. La parte pendiente es resolver el conflicto y aportar o aceptar prueba de comportamiento real antes del merge.
