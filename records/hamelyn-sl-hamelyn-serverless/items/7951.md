## Label Justifications

- `P1`: Un check verde puede permitir merges con una prueba fallida, bloqueada o todavía no concluida.
- `impact:security`: El flujo instala código de una PR no confiable sin desactivar explícitamente lifecycle scripts.

## Summary

La incidencia sigue vigente: el workflow da por aceptado el HTTP 202 y no espera el resultado terminal de la misma ejecución, por lo que no ofrece una señal de merge fiable.

## What This Changes

Corregir PR Proof para publicar evidencia trazable y hacer que PR Lifecycle espere y refleje el veredicto terminal del run probado.

## Best Possible Solution

Persistir un run inmutable por `runId` y `expectedHeadSha`, esperar su terminalidad desde el workflow y publicar artefactos con comandos, salidas, hashes y resultado esperado/observado.

Likely owner: JavierHamelyn

Owner confidence: high

Options:

- **Hacer Proof bloqueante y trazable (recommended):** Esperar el mismo `runId` hasta estado terminal, fallar ante evidencia insuficiente y desactivar lifecycle scripts durante instalaciones de PRs.
- **Mantenerlo informativo:** Conservar el comportamiento asíncrono, pero etiquetar explícitamente que la tarjeta no es una señal apta para merge.
- **Pausar Proof automático:** Desactivar la invocación automática hasta disponer de trazabilidad y aislamiento suficientes.

## Reproduction Assessment

Sí, por inspección de código: el workflow termina tras `accepted=true` y la ruta ejecuta la prueba después de responder. Falta una ejecución controlada para medir los timeouts reales.

## Solution Assessment

No. La señal actual solo prueba aceptación; la solución debe enlazar workflow, `runId`, SHA esperado, evidencia inmutable y estado terminal.
