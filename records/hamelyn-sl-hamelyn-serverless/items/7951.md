## Label Justifications

- `P1`: El workflow de validación de PR puede informar éxito antes de conocer un fallo terminal real.
- `impact:security`: La instalación del checkout no confiable mantiene habilitados lifecycle scripts de pnpm.
- `impact:other`: La evidencia de Proof carece de la trazabilidad necesaria para respaldar decisiones de revisión.

## Summary

El problema sigue presente en `dev`: el check acredita la aceptación HTTP y no un veredicto terminal. Personas relacionadas: JavierHamelyn y MiguelHamelyn.

## What This Changes

El issue pide que PR Proof espere el resultado terminal, publique evidencia verificable por ejecución y endurezca el sandbox frente a código de PR no confiable.

## Best Possible Solution

Diseñar un contrato durable por `runId` y SHA que haga fallar o concluir explícitamente el check, preserve un manifiesto inmutable de ejecución y use instalación aislada sin scripts.

## Maintainer Decision

Rationale: La corrección cruza semántica de checks, costes de ejecución, retención de artefactos y la frontera de seguridad del sandbox; no es una decisión mecánica de código.

Likely owner: JavierHamelyn

Owner confidence: high

Options:

- **Adoptar contrato fail-closed (recommended):** Esperar el estado terminal del mismo `runId`, fallar ante evidencia ausente y persistir manifiestos verificables por ejecución.
- **Mantener modo informativo:** Conservar Proof no bloqueante, pero diferenciar claramente aceptación, resultado terminal y evidencia insuficiente en el check y el body.

## Reproduction Assessment

Sí, a nivel de código: una PR elegible recibe 202 tras `after()` y el workflow solo valida `accepted` o `skipped`, sin esperar el resultado.

## Solution Assessment

No como cambio aislado: la dirección es correcta, pero debe dividirse en una frontera segura de instalación y un contrato de estado/evidencia decidido por plataforma.
