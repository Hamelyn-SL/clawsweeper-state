## Label Justifications

- `P0`: The checkout currently lets a manipulated client lower shipping or total amounts before payment, which is a payment integrity/security bypass.
- `impact:security`: The issue is about a missing server-side trust boundary for client-supplied checkout amounts used for payment.

## Summary

Keep open: current dev still trusts checkout pricing fields from the client before persisting the checkout, and the related draft PR only extracts/document tests without changing behavior.

## What This Changes

The issue asks the ecommerce checkout API to recalculate shipping, new-product surcharge, coupons, and total server-side before persisting or charging.

## Best Possible Solution

Move the ecommerce shipping and total calculation into a shared server-side domain service, call it in POST /api/v5/checkout before saving, and reject or explicitly reconcile mismatches with BL specs and tests updated in the same fix.

## Maintainer Decision

Required: true

Kind: security_boundary

Question: Should checkout amount mismatches fail closed before persistence, or should the server recalculate and overwrite the submitted totals?

Rationale: Both choices fix the client-trust boundary, but they have different customer-facing failure behavior, analytics impact, and compatibility implications for cached checkout clients.

Likely owner: PabloMoran34

Owner reason: The issue came from the Shipping Costs BL owner workflow, and the decision affects the validated BL spec for this rule.

Owner confidence: high

Options:

- **Reject mismatches before save (recommended):** Return a clear 400-style checkout error when client-sent shipping or total differs from the server calculation, preventing underpayment and surfacing stale client bugs.
- **Recalculate and overwrite totals:** Persist and charge the server-calculated values while logging the discrepancy, reducing customer interruption but hiding client drift unless monitored.
- **Sequence after BL extraction:** Wait for the draft BL extraction PR to land first, then implement the enforcement as a smaller follow-up on top of the shared pure functions.

## Reproduction Assessment

Yes, from source inspection: POST /api/v5/checkout copies client-sent shippingCost, newProductsShippingCost, and totalPrice into the saved checkout, and both payment providers then charge that stored total. I did not run a live checkout, but the vulnerable path is explicit in current dev.

## Solution Assessment

No, the current implementation is not the right solution because it validates coupon/PUDO details but not the payment amount boundary. The maintainable fix is to share the checkout pricing calculation server-side and enforce it before persistence/payment.
