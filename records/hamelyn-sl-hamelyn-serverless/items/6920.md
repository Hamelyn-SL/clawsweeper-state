## Label Justifications

- `P0`: El checkout permite que un cliente manipulado altere importes que después alimentan el cobro, una frontera de seguridad/pago crítica.
- `impact:security`: La issue trata de validación server-side de importes de pago frente a valores enviados por cliente.

## Summary

Mantener abierta: en `dev` el checkout sigue persistiendo importes controlados por el cliente y los flujos de Stripe/Mercado Pago siguen cobrando desde ese checkout guardado. La PR relacionada actual recoloca reglas BL sin cambio de comportamiento, así que no cierra este agujero de validación.

## What This Changes

La issue pide recalcular en servidor el coste de envío, el recargo de productos nuevos y el total del checkout antes de persistir o cobrar.

## Best Possible Solution

Centralizar el cálculo server-side del checkout en una función pura compartida, ejecutar esa validación antes de persistir y de iniciar pagos, rechazar discrepancias con un error claro y actualizar la spec `BL-ecommerce-checkout-24` con pruebas BL y de endpoint.

Options:

- **Rechazar fail-closed (recommended):** Recalcular en servidor y devolver error cuando `shippingCost`, `newProductsShippingCost` o `totalPrice` no coincidan con la tarifa esperada, dejando el cliente volver a calcular.
- **Corregir y continuar:** Recalcular en servidor, sobrescribir los importes persistidos y cobrar el importe servidor, aceptando el riesgo de sorpresa en el cliente si la UI mostró otro total.
- **Tolerancia explícita:** Aceptar solo diferencias menores documentadas, por ejemplo redondeo de moneda, y rechazar cualquier discrepancia material.

## Reproduction Assessment

Sí, a nivel de fuente: `POST /api/v5/checkout` copia los importes del body y los endpoints de pago leen después `checkout.totalPrice`. No ejecuté un checkout real contra servicios de pago, pero el camino vulnerable está trazado en código actual.

## Solution Assessment

Aún no: la dirección correcta es recalcular y validar en servidor antes de persistir/cobrar, pero falta decidir el comportamiento ante discrepancias y coordinarlo con las specs/helpers BL que está moviendo la PR relacionada.
