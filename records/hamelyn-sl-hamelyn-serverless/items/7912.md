## Summary

El cambio de orquestación está razonado y la prueba cubre los modos fresh y stale, pero no debe fusionarse mientras el token REST de KV se despliega como variable de entorno ordinaria de la Cloud Function.

## What This Changes

El PR reemplaza el dispatcher BigQuery/Pub/Sub por un marcador de frescura en KV, encadena la materialización de stocks en `hamelyn-bq-merge` y programa Flash Offers con fallback stale.

## Best Possible Solution

Guardar el token KV en Secret Manager, referenciarlo mediante `secretEnvironmentVariables` y verificar en un despliegue controlado tanto el marcador fresh como el fallback stale antes de retirar definitivamente la ruta anterior.

Options:

- **Mover el token a Secret Manager (recommended):** Crear o reutilizar un secreto de GCP, declararlo en `secretEnvironmentVariables` y conceder al runtime solo el acceso mínimo necesario.
- **Aceptar la variable de entorno actual:** Mantener el token como `environmentVariables` y documentar explícitamente la justificación y el perímetro IAM que puede leer la configuración.

## Reproduction Assessment

Sí, por inspección de fuente: el despliegue convierte `environmentVariables` en `--env-vars-file`, mientras que ya existe soporte para `--set-secrets`; el riesgo de credencial es verificable sin datos productivos.

## Solution Assessment

No, mientras el token KV siga como variable de entorno ordinaria; la vía de Secret Manager ya soportada ofrece el mismo comportamiento con un límite de acceso más apropiado.
