## Label Justifications

- `P2`: Es una mejora operativa planificada para Supply con bloqueos relevantes, pero no una regresión activa de producción.
- `merge-risk: 🚨 automation`: El workflow puede escribir versiones en la rama seleccionada y lanzar builds/submits, dejando repositorio y stores desalineados si faltan guardas.
- `merge-risk: 🚨 compatibility`: El script omite dos fuentes nativas de versión y el conflicto puede degradar el E2E vigente de Node 24.

## Summary

Este PR sigue siendo necesario porque `dev` aún no contiene una automatización equivalente, pero el head actual no está listo para merge: quedan defectos de seguridad de release y falta prueba real de EAS/stores. Personas probablemente relacionadas: `MiguelHamelyn` como responsable operativo y revisor asignado (confianza alta), `danielmenchen-hamelyn` por el historial de versionado y E2E de Supply (alta), y `banosdavidhamelyn` por la migración vigente del workflow a Node 24 (alta).

## What This Changes

El PR añade un workflow manual para incrementar la versión de Supply, ejecutar EAS Build + Submit en canales beta o release, configurar los destinos de las stores y documentar el proceso.

## Best Possible Solution

Mantener la automatización como workflow manual, pero obligar a usar una rama de release distinta de `dev`/`master`, sincronizar mediante el mecanismo Expo aprobado las cinco fuentes de versión efectivas, construir y enviar desde esa rama y conservar como paso manual el merge del bump después de comprobar ambos binarios live; además debe fijarse `eas-cli`, preservarse el E2E actual y limpiarse toda atribución prohibida.
