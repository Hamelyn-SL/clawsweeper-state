## Label Justifications

- `P2`: Es una mejora planificable de despliegue móvil con bloqueos importantes antes del merge, pero no una regresión activa en producción.
- `merge-risk: 🚨 automation`: El workflow puede persistir un bump antes de completar el despliegue y actualmente entra en conflicto con cambios posteriores del E2E.

## Summary

El PR sigue siendo necesario porque `dev` aún no tiene automatización EAS, pero la rama no está lista para merge: adelanta el anuncio de versión, deja incompleta la sincronización de versiones de marketing, está en conflicto con `dev` y carece de prueba real. La dirección es útil, aunque requiere corregir el protocolo de release y resolver la autorización de la lane de producción.

## What This Changes

El PR añade un workflow manual de EAS Build/Submit con selectores de plataforma, lane y bump, un script de versionado, perfiles de submit, documentación y un cambio de Node en el E2E de Supply.

## Best Possible Solution

Implementar un release en dos fases desde una rama explícita: sincronizar y validar todas las fuentes de versión mediante la configuración Expo, construir y enviar con toolchain fijada y entorno protegido, y fusionar el bump en `dev` solo después de confirmar ambos binarios live.
