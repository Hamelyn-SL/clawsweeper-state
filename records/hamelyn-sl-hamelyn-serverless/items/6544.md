## Label Justifications

- `P2`: Es una mejora operativa planificable para Supply; no existe una interrupción actual, pero debe corregirse antes de sustituir el proceso manual.
- `merge-risk: 🚨 compatibility`: El workflow puede publicar o registrar una versión visible distinta entre Expo/JS y los proyectos nativos, y además parte de runtimes anteriores a Node 24.
- `merge-risk: 🚨 security-boundary`: El mismo job dispone de `contents: write`, ejecuta una acción y CLI externas y recibe credenciales capaces de enviar binarios a stores.
- `merge-risk: 🚨 automation`: Las carreras por rama, el push previo al build y las escrituras parciales pueden dejar versiones consumidas o ejecuciones fallidas de forma no resuelta por CI.

## Summary

El trabajo sigue siendo necesario porque `dev` aún no contiene un pipeline equivalente, pero este PR no está listo para merge: conserva defectos de versionado y concurrencia ya señalados, escribe en la rama antes de validar la publicación, entra en conflicto con la migración actual a Node 24 y no aporta prueba real de EAS/ stores. Además, el cuerpo y dos commits contienen atribución de herramientas de IA prohibida por la política del repositorio.

## What This Changes

El PR añade un workflow manual de EAS Build + Submit para Supply con selectores de plataforma, canal e incremento de versión, junto con perfiles de envío y documentación operativa.

## Best Possible Solution

Mantener una beta manual como ruta inicial, sincronizar o regenerar atómicamente las cinco fuentes de versión que realmente llegan al binario, empujar solo a una rama de release tras una publicación correcta, serializar por rama, conservar Node 24 y proteger `lane: release` mediante un Environment con aprobación y permisos separados.
