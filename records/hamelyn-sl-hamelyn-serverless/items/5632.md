## Label Justifications

- `P1`: Un cron de producción de alta frecuencia queda bloqueado recurrentemente y termina en `504` después de consumir los 800 segundos completos.
- `impact:crash-loop`: Las invocaciones pierden disponibilidad y permanecen colgadas hasta que Vercel finaliza forzosamente el proceso.

## Summary

Debe mantenerse abierta: la corrección fusionada solo normalizó las rutas, la incidencia reapareció después y `dev` continúa esperando todas las fases de Amazon COM sin un presupuesto temporal efectivo. No hay otro issue o PR que cubra de forma canónica este timeout concreto.

## What This Changes

Evitar que `/api/amazonCOM` permanezca bloqueado hasta agotar el límite de 800 segundos de Vercel cuando una fase del cron no termina.

## Best Possible Solution

Aplicar un presupuesto temporal por fase con cancelación cooperativa en la operación que se demuestre bloqueada, dejar margen para responder antes de los 800 segundos y registrar una respuesta controlada con fase, duración y causa; además, debe evitarse el solape de ejecuciones mientras una anterior siga activa.

## Maintainer Decision

Required: false

## Reproduction Assessment

Sí, con alta confianza desde la fuente: basta con que una de las fases devuelva una promesa que no resuelve para que el handler espere indefinidamente, y la discusión aporta múltiples ejecuciones reales que alcanzaron exactamente 800 segundos. No se ha ejecutado una reproducción local que identifique la fase concreta.

## Solution Assessment

No; el PR anterior normalizó rutas, pero no limitó ni canceló las fases, y un timeout exclusivo de conexión tampoco cubriría bloqueos posteriores. La solución más estrecha y segura debe partir de los logs de fase y añadir un límite cancelable en la operación demostrada o en un contrato común que preserve las fases largas válidas.
