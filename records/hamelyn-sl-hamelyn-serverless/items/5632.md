## Label Justifications

- `P1`: La ruta de producción llegó repetidamente al límite completo de Vercel y dejó ejecuciones de marketplace sin completar.
- `impact:crash-loop`: El problema se manifiesta como agotamiento de runtime y 504 en una ruta de cron.

## Summary

Debe mantenerse abierta: la normalización de rutas se fusionó, pero la firma de 800 segundos reapareció y el handler actual aún espera todas las fases Amazon sin un límite de ejecución compartido.

## What This Changes

La issue informa de ejecuciones de `/api/amazonCOM` que alcanzan el límite de 800 segundos de Vercel.

## Best Possible Solution

Añadir al handler compartido un presupuesto de ejecución observable para cada fase Amazon, con cancelación o reintento diferido y un resultado explícito para trabajo parcial.

Owner confidence: high

Options:

- **Acotar y diferir (recommended):** Aplicar un presupuesto compartido por fase, registrar el corte y reintentar de forma explícita el trabajo no completado.
- **Mantener ejecución completa:** Conservar los 800 segundos actuales y aceptar los 504 mientras se investigan las operaciones lentas por separado.
- **Presupuesto solo para conexión:** Limitar únicamente Mongo y mantener sin límite las fases posteriores de Amazon.

## Reproduction Assessment

No con alta confianza: existe evidencia de producción y el flujo sin límite es visible en código, pero falta reproducir la degradación de Mongo o una fase Amazon bloqueada en un entorno controlado.

## Solution Assessment

No; la normalización de rutas evita guards locales divergentes, pero no limita la espera de las fases. La solución debe centrarse en el handler común con una política operativa explícita.
