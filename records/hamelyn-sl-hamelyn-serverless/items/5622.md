## Summary

La issue sigue siendo necesaria: el handler compartido mantiene HTTP 200 cuando hay rechazos parciales; la respuesta estructurada reciente mejora el diagnóstico, pero no define severidad ni una señal operativa común.

## What This Changes

Definir un contrato de severidad y observabilidad para rechazos parciales de los cron jobs compartidos.

## Best Possible Solution

Acordar primero una clasificación compatible por fase o ruta; emitir un resumen estructurado común y endurecer HTTP o alertas solo donde el fallo parcial no sea tolerable.

Options:

- **Señal compatible primero (recommended):** Mantener HTTP 200 inicialmente y normalizar `status`, recuentos y severidad para decidir después las rutas que deben fallar.
- **Endurecer rutas críticas:** Definir ahora una lista reducida de rutas o fases cuyo rechazo parcial devuelva 207/5xx y probar su comportamiento de reintento.
- **Conservar el contrato actual:** Mantener HTTP 200 y logs actuales, aceptando que la detección operativa seguirá dependiendo de consultas y alertas específicas.

## Reproduction Assessment

Sí, por inspección de código: un rechazo parcial alcanza la respuesta con HTTP 200 en App Router y en el handler legacy. No se ejecutó un cron de producción durante esta revisión de solo lectura.

## Solution Assessment

No, un cambio global inmediato a 207/5xx no es la solución más segura; primero hace falta una política compatible que clasifique rutas y fallos tolerables.
