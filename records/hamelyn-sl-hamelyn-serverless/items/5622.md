## Label Justifications

- `P1`: El contrato común puede ocultar fallos repetidos en rutas de cron de producción y retrasa la detección operativa.
- `impact:other`: El impacto demostrado es observabilidad y alertado operacional degradados, fuera de las categorías específicas disponibles.

## Summary

La incidencia sigue siendo necesaria: el handler compartido conserva HTTP 200 para rechazos parciales y aún no define la severidad ni la señal analítica común solicitadas.

## What This Changes

Definir un contrato común para que los crons comuniquen y registren de forma estructurada los fallos parciales sin ocultar degradaciones operativas.

## Best Possible Solution

Acordar primero una taxonomía de severidad compatible y aplicar una respuesta, log y métrica estructurados comunes; después endurecer por ruta solo los casos acordados.

Options:

- **Fase compatible estructurada (recommended):** Mantener HTTP 200 temporalmente y añadir `status`, contadores, razones y severidad consultables antes de endurecer rutas.
- **Endurecer rutas críticas ahora:** Definir una lista explícita de rutas o fases cuyo rechazo parcial devuelva 207/5xx desde la primera entrega.
- **Conservar el contrato actual:** Mantener el diagnóstico actual basado en logs, aceptando que la salud HTTP no represente fallos parciales.

## Reproduction Assessment

Sí, por inspección de código: una ruta que entregue al handler una promesa rechazada responde HTTP 200 con resumen parcial. La evidencia de producción aportada refuerza esa ruta.

## Solution Assessment

No para un cambio global inmediato de estado HTTP. La vía más segura es fijar primero la política de severidad y compatibilidad compartida.
