## Label Justifications

- `P1`: La señal HTTP oculta degradaciones recurrentes de crons compartidos en producción y dificulta detectar fallos materiales de sincronización y procesamiento.
- `impact:other`: La issue afecta de forma concreta a la observabilidad y al alertado operativo de crons, un impacto no cubierto por las categorías específicas disponibles.

## Summary

La issue sigue siendo necesaria: `dev` aún devuelve HTTP 200 cuando hay rechazos parciales y no existe una política compartida de severidad por ruta. Las mejoras ya fusionadas aportan resumen estructurado y temporización por fase, pero no resuelven la señal operacional ni la decisión de compatibilidad planteada.

## What This Changes

Definir y aplicar una señal estructurada y una política explícita de severidad y estado HTTP para fallos parciales en los handlers compartidos de cron.

## Best Possible Solution

Introducir primero un resultado estructurado compatible en ambos handlers —estado, recuentos, razones sanitizadas y severidad— manteniendo HTTP 200 por defecto; después permitir que cada ruta declare explícitamente qué severidades deben elevar 207/5xx, con documentación y validación en BigQuery.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Debe la primera fase conservar HTTP 200 por defecto y añadir solo señal estructurada, o debe elevar ya 207/5xx para severidades o rutas seleccionadas?

Rationale: La fuente confirma el problema de observabilidad, pero no permite deducir qué fallos parciales son tolerables según cada flujo de negocio; una decisión global puede cambiar reintentos, alertas y compatibilidad de 39 rutas.

Likely owner: JavierHamelyn

Owner reason: Es la persona con trabajo más reciente tanto en el contrato común de rutas como en la observabilidad por fase, además de haber desarrollado el análisis de política de esta issue.

Owner confidence: high

Options:

- **Señal compatible primero (recommended):** Añadir `status`, recuentos, razones sanitizadas y `severity` en ambos handlers, manteniendo HTTP 200 por defecto hasta clasificar las rutas.
- **Elevación selectiva inicial:** Añadir la señal estructurada y declarar desde la primera entrega una lista acotada de rutas o severidades que respondan 207/5xx.
- **Fallo global estricto:** Hacer que cualquier rechazo parcial cambie inmediatamente el estado HTTP de todos los consumidores del handler compartido.

## Reproduction Assessment

Sí, a nivel de fuente y con alta confianza: cualquier método rechazado produce `Completed with partial failures` y un `executionSummary` con rechazos, pero la respuesta continúa fijada a HTTP 200. No se ejecutó una llamada real porque la revisión era estrictamente read-only.

## Solution Assessment

No está decidido por completo. La vía más segura y mantenible separa una primera señal estructurada compatible de una política optativa por ruta, en lugar de imponer 5xx globalmente sin clasificar los fallos tolerables.
