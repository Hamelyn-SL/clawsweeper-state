## Summary

La incidencia sigue siendo necesaria: el handler compartido continúa devolviendo HTTP 200 tras rechazos parciales y la semántica de severidad por ruta aún requiere una decisión humana.

## What This Changes

La incidencia solicita un contrato estructurado y una política explícita para comunicar fallos parciales de los crons compartidos.

## Best Possible Solution

Acordar primero un sobre compatible con `status`, contadores y severidad; después aplicar una matriz explícita por ruta o fase para decidir cuándo elevar HTTP 207 o 5xx.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿La primera fase debe conservar HTTP 200 con señal estructurada, o qué rutas y severidades deben pasar ya a HTTP 207 o 5xx?

Rationale: El handler cubre decenas de rutas y los rechazos parciales pueden ser tolerables o críticos según la fase de negocio; el código no puede inferir esa política con seguridad.

Likely owner: JavierHamelyn

Owner reason: El historial del handler vigente y la investigación de esta incidencia le conectan directamente con la decisión del contrato común.

Owner confidence: high

Options:

- **Señal compatible primero (recommended):** Añadir `status`, `rejectedCount`, motivos y severidad manteniendo temporalmente HTTP 200, para basar después la política por ruta en datos reales.
- **Elevar rutas críticas:** Definir ahora una lista pequeña de fases críticas que devuelvan 207 o 5xx cuando fallen parcialmente.
- **Mantener contrato actual:** Conservar HTTP 200 y depender de logs por integración, aceptando que la degradación seguirá sin una señal común.

## Reproduction Assessment

Sí, a nivel de código: basta con una promesa rechazada para que el handler genere `executionSummary.rejected > 0` y responda HTTP 200.

## Solution Assessment

No, un cambio global de código HTTP no es todavía la mejor solución: hace falta clasificar primero qué rechazos parciales son tolerables por ruta y fase.
