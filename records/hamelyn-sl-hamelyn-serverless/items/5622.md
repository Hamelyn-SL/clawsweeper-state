## Summary

La issue sigue siendo necesaria: el handler de App Router aún devuelve HTTP 200 cuando hay rechazos parciales, aunque ahora exponga `executionSummary` y `rejectedReasons`; el handler legacy también conserva HTTP 200 sin ese resumen. No hay una política compartida que distinga fallos tolerables de degradaciones que deban alertar o fallar la ruta.

**Personas probablemente relacionadas**
- `JavierHamelyn` (confianza alta): añadió el handler compartido actual y el resumen estructurado, por lo que es el mejor punto de partida para encauzar la decisión de contrato.

## What This Changes

La issue propone definir la severidad y la señal estructurada de los fallos parciales de crons para evitar que ejecuciones degradadas parezcan sanas con HTTP 200.

## Best Possible Solution

Acordar primero un contrato compatible de respuesta y observabilidad para ambos handlers —estado estructurado, número y razones de rechazos, severidad y métrica consultable— y después habilitar HTTP no-2xx solo para rutas o fases cuya política lo requiera, con documentación para `marketplace-crons` y `data-crons`.

Rationale: El código confirma el comportamiento, pero no puede decidir qué rechazos son tolerables por negocio ni qué consumidores externos dependen hoy de HTTP 200.

Options:

- **Señal compatible primero (recommended):** Mantener HTTP 200 temporalmente y añadir `status`, conteos, razones, severidad y una métrica consultable para clasificar rutas con datos reales.
- **Endurecer rutas críticas ahora:** Definir una lista inicial de rutas o fases donde un rechazo parcial devuelve 207/5xx, asumiendo y documentando su impacto de compatibilidad.

## Reproduction Assessment

Sí, a nivel de código y con alta confianza: cualquier cron de App Router con al menos una promesa rechazada genera `executionSummary.rejected > 0` y responde HTTP 200. El handler legacy mantiene el mismo estado de éxito sin exponer el resumen.

## Solution Assessment

No, un cambio global e inmediato de HTTP status no es la mejor solución porque el contrato abarca muchas rutas con tolerancias de negocio distintas. La vía más segura es fijar primero una señal estructurada compatible y una política explícita por ruta o fase.
