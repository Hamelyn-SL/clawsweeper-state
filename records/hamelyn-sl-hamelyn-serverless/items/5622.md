## Label Justifications

- `P1`: Los fallos parciales activos de crons críticos quedan invisibles para alertas basadas en HTTP y dificultan detectar degradaciones operativas reales.
- `impact:other`: La issue afecta a la observabilidad y clasificación operacional de ejecuciones programadas, un impacto transversal no cubierto por las etiquetas específicas disponibles.

## Summary

La issue sigue siendo necesaria: `dev` aún responde HTTP 200 ante rechazos parciales y no existe una política común de severidad por ruta. El resumen estructurado añadido en abril y los logs de duración por fase añadidos en junio mejoran el diagnóstico, pero no resuelven la señal operacional ni la decisión de compatibilidad planteada.

## What This Changes

Definir un contrato común de severidad y observabilidad para que los crons distingan ejecuciones correctas, degradadas y fallidas sin ocultar rechazos parciales tras HTTP 200.

## Best Possible Solution

Adoptar primero un resultado estructurado compatible en ambos handlers (`ok`, `partial_failure`, `failed`, recuentos, razones sanitizadas y severidad), manteniendo 200 por defecto; después permitir que cada ruta declare explícitamente qué severidades elevan 207/5xx, con documentación y validación de consultas en BigQuery.

Question: ¿Debe la primera fase mantener HTTP 200 para todos los parciales y añadir solo señal estructurada, o deben algunas rutas o severidades elevar ya 207/5xx?

Rationale: La fuente confirma el defecto de observabilidad, pero no permite deducir qué fallos parciales son tolerables según negocio; una decisión global puede cambiar reintentos, alertas y compatibilidad de numerosos crons.

Owner confidence: high

Options:

- **Señal compatible primero (recommended):** Añadir el contrato estructurado en ambos handlers, conservar HTTP 200 por defecto y posponer 207/5xx hasta clasificar rutas y severidades.
- **Elevación selectiva inicial:** Añadir el contrato estructurado y declarar desde la primera entrega una lista reducida de rutas o severidades que devuelvan 207/5xx.
- **Fallo global estricto:** Hacer que cualquier rechazo parcial cambie inmediatamente el estado HTTP para todos los consumidores del handler compartido.

## Reproduction Assessment

Sí en fuente, con alta confianza: cualquier método rechazado en `cronHandlerAppRouter` produce `Completed with partial failures`, pero la respuesta sigue fijada a HTTP 200; no se ejecutó una llamada real por tratarse de una revisión de solo lectura.

## Solution Assessment

No está decidido todavía. La vía más segura es separar la señal estructurada compatible de la política optativa por ruta, en vez de cambiar globalmente a 5xx sin clasificar los fallos tolerables.
