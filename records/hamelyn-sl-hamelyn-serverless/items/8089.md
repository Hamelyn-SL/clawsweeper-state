## Label Justifications

- `P1`: Dos estaciones pueden preparar el mismo tipo con etiquetas duplicadas y el packing puede agrupar productos de carros físicos distintos.
- `impact:other`: El impacto principal es una preparación física incorrecta de pedidos, fuera de las clases específicas de datos, mensajes, sesión o proveedor.

## Summary

La incidencia sigue siendo necesaria: `dev` mantiene contadores por estación que pueden producir la misma etiqueta y el packing aún ignora la etiqueta solicitada al resolver los pedidos.

## What This Changes

La incidencia pide reservar carros secuenciales globales por tipo y usar la etiqueta persistida para que dos estaciones no colisionen ni mezclen productos al hacer packing.

## Best Possible Solution

Implementar una reserva atómica e idempotente por tipo, persistir la etiqueta confirmada en ambos modelos y resolver packing por coincidencia exacta, conservando un fallback inequívoco para datos legacy.

## Maintainer Decision

Required: false

## Reproduction Assessment

Sí, desde código con alta confianza: dos contadores de estación con el mismo valor derivan el mismo carro y packing descarta el contenedor exacto. Falta una ejecución aislada contra KV/Mongo para marcarla como reproducida en runtime.

## Solution Assessment

Sí, en dirección: la etiqueta física persistida debe ser la fuente de verdad. La reserva debe diseñarse como transición atómica e idempotente y mantener compatibilidad explícita para registros legacy.
