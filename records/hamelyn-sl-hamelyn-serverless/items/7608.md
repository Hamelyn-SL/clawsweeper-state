## Summary

La PR sigue siendo necesaria porque `dev` no contiene la capacidad solicitada, pero no está preparada para merge: la redelivery puede volver a ejecutar el carrier con el mismo `attempt`, rompiendo el límite funcional de tres reintentos. También debe corregirse la guía operacional y aportarse prueba real.

## What This Changes

La PR añade reintentos automáticos selectivos y acotados para fallos transitorios de creación de etiquetas, con validación Zod, selección de incidencias, tests y documentación de shipping.

## Best Possible Solution

Separar la recuperación de publicación del efecto externo —o persistir qué intento ya se ejecutó— para que una redelivery reenvíe el retry pendiente sin volver a llamar al carrier, manteniendo un máximo real de tres retries por pedido.

No todavía. Reencolar únicamente IDs retriables es una frontera adecuada, pero usar la redelivery para recuperar un fallo de publicación vuelve a ejecutar el efecto externo y rompe el límite funcional de tres retries.
