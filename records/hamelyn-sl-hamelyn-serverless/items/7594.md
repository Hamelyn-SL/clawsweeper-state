## Label Justifications

- `P2`: El incidente exige recuperación manual de pedidos concretos, pero no bloquea de forma general la creación de etiquetas y conserva un backstop operativo.
- `impact:other`: Los fallos transitorios dejan pedidos sin etiqueta hasta que operaciones los relanza manualmente, un impacto operativo claro que no encaja en las categorías específicas.

## Summary

La issue sigue siendo necesaria: el `dev` actual clasifica ciertos errores como retriables, pero los fallos parciales por pedido se reducen a contadores y el consumidor confirma el mensaje sin reencolarlos. Tampoco existe una PR vinculada ni otro elemento canónico que posea este trabajo.

## What This Changes

La issue solicita reintentos automáticos, acotados y con backoff para pedidos cuya creación de etiqueta falla por un error transitorio del carrier.

## Best Possible Solution

Implementar un reintento genérico por subconjunto fallido que devuelva los IDs retriables, reencole con `attempt` y delay acotado, permita `LABEL_ISSUE` solo en modo retry y mantenga las defensas contra etiquetas duplicadas.

## Maintainer Decision

Required: false

## Reproduction Assessment

Sí a nivel de fuente, con alta confianza: `processCarrierLabels` reduce los fallos a un contador y el handler de cola solo provoca redelivery para errores fatales. No se ha ejecutado una reproducción real contra Cainiao.

## Solution Assessment

Sí en dirección general: reencolar únicamente los IDs marcados como retriables evita repetir pedidos correctos y conserva el backstop manual para errores permanentes. La implementación debe separar explícitamente el barrido inicial del modo retry.
