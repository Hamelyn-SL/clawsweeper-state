## Summary

Mantener abierta: la corrección fusionada resolvió el mapeo de la variante `offerId`, pero los `400` posteriores siguen requiriendo aislar su payload remoto y el cron aún devuelve HTTP 200 ante rechazos parciales.

## What This Changes

Corregir la clasificación de los `400` de eBay durante `updatePrice` y evitar que los fallos parciales sostenidos parezcan ejecuciones sanas del cron.

## Best Possible Solution

Conservar el mapeo ya fusionado, capturar de forma redacted el cuerpo de un `400` reciente y definir en https://github.com/Hamelyn-SL/hamelyn-serverless/issues/5622 una señal estructurada compatible para fallos parciales.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Qué contrato deben exponer los crons cuando `updatePrice` deja SKUs sin sincronizar: HTTP 200 con estado estructurado, un código degradado o un error por severidad/ruta?

Rationale: La implementación específica ya distingue errores permanentes y transitorios, pero el cambio de respuesta afecta rutas y alertas compartidas; no es una decisión segura para automatizar desde una sola integración.

Likely owner: JavierHamelyn

Owner confidence: high

Options:

- **Mantener 200 con señal estructurada (recommended):** Conservar compatibilidad HTTP y añadir un estado consultable de fallo parcial, conteos y severidad para alertas y BigQuery.
- **Degradar según severidad:** Devolver una respuesta no exitosa solo cuando el umbral de SKUs fallidos o la fase de negocio lo requiera.
- **Fallar toda ejecución parcial:** Tratar cualquier rechazo parcial como error HTTP, simplificando alertas a costa de cambiar el contrato actual.

## Solution Assessment
