## Label Justifications

- `P1`: The Milanuncios responder can skip full scheduled executions while still returning HTTP 200, affecting a live message-response workflow.
- `impact:message-loss`: When the cron fails before login/session completion, pending Milanuncios conversations may not receive automated replies in that run.
- `impact:other`: The cron wrapper currently hides a total single-task failure as a partial-success HTTP response, weakening operational observability.

## Summary

Keep open: current `dev` still matches the reported failure mode, with raw non-timeout `fetch failed` errors before message loading and a generic `200` partial-failure response when the only Milanuncios task rejects.

## What This Changes

The issue asks for phase-aware, observable failure handling when `/api/milanuncios-responder` gets `fetch failed` before it reaches pending-message loading.

## Best Possible Solution

Keep the existing pending-message deferral behavior, but make pre-login/login/session fetch failures phase-aware and return an explicit failing cron response when the sole Milanuncios task cannot run.

## Maintainer Decision

Required: false

## Reproduction Assessment

Yes from source plus production evidence: the issue records real BigQuery failures, and current code still rethrows non-timeout `fetch failed` without phase context while the shared cron wrapper returns HTTP 200 for rejected task promises.

## Solution Assessment

Yes: a narrow route/controller fix can wrap non-timeout fetch errors with the action name and make this single-task cron fail explicitly, without changing the separately tracked pending-message timeout behavior.
