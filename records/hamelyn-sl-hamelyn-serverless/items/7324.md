## Label Justifications

- `P0`: El flujo activo de producción puede aceptar incidencias de clientes con `201` aunque el mensaje no llegue a eDesk, lo que bloquea atención al cliente y causa pérdida operativa de mensajes.
- `impact:message-loss`: La issue trata de mensajes de incidencias que no quedan visibles en el canal operativo de eDesk tras un `429` en `POST /messages`.

## Summary

Mantendría abierta esta issue: en `dev` sigue existiendo el fallo central, porque el cliente compartido de eDesk no reintenta `429` y el pipeline de incidencias puede registrar el ticket como éxito aunque falle el mensaje. La actualización operativa con BigQuery convierte el problema en pérdida operativa de mensajes, no en una mejora opcional.

## What This Changes

La issue pide que las incidencias nuevas de ecommerce no lleguen vacías a eDesk cuando `POST /messages` falla por rate limit, y que el flujo compartido no devuelva un falso `201`.

## Best Possible Solution

Centralizar retry/backoff acotado para `429` en el cliente eDesk compartido y hacer que el pipeline devuelva error operativo cuando el mensaje no se crea tras agotar reintentos, preservando logs de recuperación y la protección contra duplicados.
