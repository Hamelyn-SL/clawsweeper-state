## Label Justifications

- `P1`: La pérdida de enlaces de tracking, Admin y Stripe en tickets activos rompe un flujo operativo de soporte ecommerce, aunque todavía falta correlación de casos concretos.
- `impact:data-loss`: El síntoma reportado es desaparición u omisión de metadatos del ticket que el código intenta enviar a eDesk.
- `impact:ux-friction`: Soporte puede seguir recibiendo el ticket, pero pierde accesos directos críticos y necesita investigar manualmente.

## Summary

No propongo cerrar este issue: el código actual sí construye los campos personalizados de eDesk y existe un fallback que puede crear el ticket sin ningún `customFields`, pero la investigación previa no pudo vincular la captura con un ticket concreto ni demostrar que el fallback se activase en ecommerce.

## What This Changes

El reporte pide investigar por qué algunos tickets de incidencias ecommerce en eDesk pierden campos personalizados como tracking, Admin URL y Stripe.

## Best Possible Solution

Mantener el issue abierto hasta tener tickets concretos; con esa evidencia, comprobar logs por ticket y, si el fallback es la causa, degradar los campos rechazados al `bodyHtml` o reintentar solo sin el campo problemático.

## Maintainer Decision

Required: false

## Reproduction Assessment

No tenemos una reproducción de alta confianza del caso reportado con un ticket real. Sí hay una ruta fuente plausible: si eDesk rechaza `custom_fields` con `400`, el código reintenta con `customFields: []`, pero el triage no encontró esa señal en logs ecommerce para el periodo revisado.

## Solution Assessment

No está claro aún cuál es la mejor corrección porque falta identificar tickets afectados. La alternativa más mantenible, si se confirma el fallback, sería conservar los datos degradándolos al cuerpo del mensaje o eliminar solo el campo rechazado, no perder todos los campos.
