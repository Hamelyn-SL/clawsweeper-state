## Label Justifications

- `P1`: El timeout repetido interrumpe un cron de producción que procesa notificaciones de pedidos cada tres minutos.
- `impact:crash-loop`: La evidencia de producción muestra ejecuciones recurrentes que agotan el runtime y terminan en `504`.

## Summary

Mantener abierta: `dev` limita el presupuesto antes de recibir otro lote, pero puede procesar todos los mensajes ya recibidos sin comprobar el margen; una secuencia lenta aún puede alcanzar los 150 segundos antes del borrado SQS.

## What This Changes

La incidencia pide evitar que `/api/amazon-notifications-pull` agote el runtime de Vercel al procesar notificaciones SQS lentas.

## Best Possible Solution

Añadir un guard de presupuesto antes de cada mensaje, retener los restantes con una razón observable y ejecutar el borrado SQS de los ya completados antes de salir.

## Solution Assessment
