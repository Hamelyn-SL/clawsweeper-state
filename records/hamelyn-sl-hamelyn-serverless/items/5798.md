## Label Justifications

- `P1`: Los timeouts repetidos de un cron que procesa notificaciones Amazon interrumpen un flujo operativo real, pero la siguiente ejecución programada ofrece recuperación parcial.
- `impact:crash-loop`: La firma observada es un agotamiento terminal del runtime de Vercel que deja la ejecución del cron en 504.

## Summary

Mantener abierta: `dev` reserva presupuesto antes de recibir cada batch, pero no entre mensajes del mismo batch; una notificación lenta o varias `ORDER_CHANGE` consecutivas aún pueden consumir los 150 segundos antes del borrado SQS. La única propuesta que cubría ese hueco, https://github.com/Hamelyn-SL/hamelyn-serverless/pull/5799, se cerró sin fusionarse.

## What This Changes

Evitar que `/api/amazon-notifications-pull` agote el runtime de 150 segundos mientras procesa mensajes SQS de Amazon.

## Best Possible Solution

Añadir un guard de presupuesto antes de iniciar cada mensaje, marcar los restantes como `execution_budget`, conservarlos en SQS y vaciar el borrado batch de los mensajes ya completados antes de terminar la ejecución.

Required: false

## Reproduction Assessment

No hay una repetición live reciente y controlada contra `dev`, pero sí una ruta reproducible desde código: recibir un batch con trabajo lento muestra que no existe un corte entre mensajes antes del límite de 150 segundos.

## Solution Assessment

Sí. Un guard por mensaje con retención explícita y borrado previo de los completados ataca el hueco exacto sin cambiar el contrato del cron ni introducir configuración nueva.
