- `P1`: The cron runs every three minutes and repeatedly fails in an active Amazon marketplace notification workflow.
- `impact:other`: The issue is a marketplace cron retry-retention problem with operational impact outside the more specific owned impact categories.

## Summary

This still needs work: current `dev` still turns the missing-stock Amazon `ORDER_CHANGE` path into a non-deletable `unsupported` result, so the notification can be retained for retry again.

## What This Changes

The issue asks `/api/amazon-notifications-pull` to handle Amazon `ORDER_CHANGE` notifications for missing-stock SKUs without retrying the same order indefinitely.

## Best Possible Solution

Add a narrow terminal handling path for missing-stock Amazon `OrderStatusChange/Unshipped` notifications, ideally letting the order reach the existing `TO_CANCEL`/sync-error handling or otherwise marking this data condition processed without changing transient retry behavior.

Yes from source inspection and the production log evidence in the issue: missing stock makes the formatter return no attributes, then the processor returns `canDelete: false` and the cron retains the notification. I did not execute the live cron in this read-only review.

## Solution Assessment

Yes; the narrowest maintainable solution is to classify missing-stock order formatting as a terminal business/data case while preserving retries for transient failures.
