## Label Justifications

- `P1`: El cron de producción repite una notificación no resoluble cada ciclo y degrada de forma continuada el procesamiento de pedidos Amazon.
- `impact:other`: El impacto demostrado es un bucle operativo y ruido de errores del cron, sin evidencia suficiente de pérdida confirmada de mensajes o datos.

## Summary

La incidencia sigue siendo necesaria: en `dev` un SKU inexistente hace que el formatter no devuelva atributos del pedido, el procesador responde `canDelete: false` y el consumidor retiene la notificación para reintento. La política terminal correcta —descartar con auditoría, aparcar o crear un `TO_CANCEL`— requiere una decisión de producto y operativa antes de reparar el flujo.

## What This Changes

Evitar que `/api/amazon-notifications-pull` reintente indefinidamente una notificación `ORDER_CHANGE` cuando su SKU ya no existe en stocks.

## Best Possible Solution

Definir una salida terminal y observable para `ORDER_CHANGE` sin stock —con motivo auditable y alerta deduplicada— y aplicar `TO_CANCEL` solo si el contrato de persistencia admite explícitamente pedidos sin stock resoluble.

Options:

- **Consumir con auditoría y alerta deduplicada (recommended):** Marcar la notificación como procesada, registrar el SKU y pedido ausentes y emitir una señal operativa única para evitar el bucle sin crear datos incompletos.
- **Enviar a una cola o estado de revisión:** Conservar el caso fuera del reintento normal para que operaciones pueda decidir su recuperación sin bloquear el cron.
- **Persistir como `TO_CANCEL`:** Extender el contrato de persistencia para admitir este caso únicamente si negocio necesita conservar el pedido aun sin stock resoluble.

## Reproduction Assessment

Sí, desde fuente: un `ORDER_CHANGE` cuyo `getOrder()` contiene un SKU ausente hace que el formatter no devuelva atributos y el consumidor lo retenga mediante `canDelete: false`. La discusión además aporta cinco reintentos de producción para el mismo patrón.

## Solution Assessment

No está decidido del todo: eliminar el reintento es necesario, pero permitir que la persistencia cree un `TO_CANCEL` no es automáticamente la opción más segura para un pedido sin stock resoluble.
