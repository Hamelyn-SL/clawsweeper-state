## Label Justifications

- `P1`: El cron de producción procesa pedidos Amazon cada tres minutos y el caso confirmado mantiene mensajes atascados en reintento.
- `impact:other`: El impacto principal es la fiabilidad operativa del consumidor SQS y la conciliación de pedidos, fuera de las clases de impacto más específicas.

## Summary

La incidencia sigue siendo necesaria: `dev` todavía retiene para reintento el `ORDER_CHANGE` cuando el formatter no obtiene ningún stock local, por lo que el mensaje puede volver a procesarse indefinidamente.

## What This Changes

Evitar que el cron `amazon-notifications-pull` reintente indefinidamente una notificación Amazon cuando su SKU ya no existe en stocks.

## Best Possible Solution

Definir una política explícita para pedidos Amazon sin stock ni `OrderSell`, conservar auditoría y aplicar una salida terminal diferenciada de los fallos transitorios antes de borrar el mensaje.

## Maintainer Decision

Kind: product_direction

Question: ¿Qué destino operativo debe tener un `ORDER_CHANGE` `Unshipped` cuyo SKU no existe y que tampoco tiene un `OrderSell` local: consumo terminal auditado, cola de revisión o creación/degradación controlada?

Rationale: La reparación evita el bucle, pero el destino elegido afecta a conciliación, inventario y recuperación de pedidos reales; el código no define ese contrato.

Likely owner: MarcosTerroso

Owner confidence: high

Options:

- **Consumir con auditoría y alerta única (recommended):** Eliminar el mensaje tras registrar el pedido huérfano y emitir una señal operativa deduplicada para revisión.
- **Retener para revisión controlada:** Mover el caso a una cola o estado observable con límite de reintentos, sin reprocesarlo en cada ejecución del cron.
- **Crear una venta degradada:** Persistir un `OrderSell` especial o `TO_CANCEL` solo tras definir las reglas de inventario y reconciliación.

## Reproduction Assessment

No hay una reproducción extremo a extremo contra datos actuales, pero sí una ruta clara en código: un `Unshipped` sin stock produce cero atributos y queda retenido para retry.

## Solution Assessment

Incierto: terminar el retry es necesario, pero convertirlo directamente en borrado o `TO_CANCEL` no es seguro sin decidir la política de conciliación.
