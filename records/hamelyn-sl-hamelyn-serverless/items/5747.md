## Label Justifications

- `P1`: El fallo confirmado en producción retrasa el procesamiento recurrente de pedidos Amazon, aunque la reentrega actual evita pérdida de mensajes.
- `impact:other`: El impacto principal es la fiabilidad operativa del cron de marketplace y no encaja con más precisión en las categorías específicas disponibles.

## Summary

Mantener abierta: `dev` conserva los mensajes SQS cuando `getOrder` falla, pero `getOrder` sigue haciendo una única llamada sin retry HTTP específico y no hay una corrección fusionada para esta firma. Gracias por el contexto de producción: la decisión entre reintento acotado y reentrega SQS debe ser explícita para no agravar los timeouts del mismo cron.

## What This Changes

La incidencia pide definir el tratamiento de los `500` transitorios de Amazon SP-API `getOrder` en `amazon-notifications-pull` sin perder notificaciones de SQS.

## Best Possible Solution

Mantener la retención SQS como salvaguarda y acordar una política limitada para `getOrder`: reintentar únicamente errores transitorios dentro del presupuesto restante, con telemetría por marketplace y pruebas de que el mensaje no se borra ni se duplica si se agota el margen.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Debe `getOrder` aplicar reintentos HTTP transitorios dentro del presupuesto del cron, o debe mantenerse la reentrega de SQS como único mecanismo de retry?

Rationale: Ambas opciones preservan datos, pero cambian la latencia, la presión sobre Amazon SP-API y la probabilidad de alcanzar el límite de 150 s; el código no puede resolver esa política por sí solo.

Likely owner: JavierHamelyn

Owner reason: Su historial conecta directamente con el consumidor que retiene y borra mensajes del pull.

Owner confidence: high

Options:

- **Retry acotado por presupuesto (recommended):** Aplicar `withHttpRetry` solo a errores transitorios de `getOrder`, con un límite que respete el tiempo restante del cron y conserve la reentrega SQS al agotarse.
- **Mantener solo reentrega SQS:** No añadir retry HTTP local y usar los 300 s de visibilidad para reintentar en el siguiente pull, priorizando el presupuesto del cron.

## Reproduction Assessment

No con alta confianza en local: la ruta de fallo es reproducible por código, pero el `500` depende de Amazon SP-API y la evidencia confirmada procede de producción. El estado actual sí permite verificar que un error de `getOrder` retiene el mensaje para reentrega.

## Solution Assessment

Incierto: envolver incondicionalmente `getOrder` con retry no es necesariamente la mejor solución porque comparte presupuesto con el timeout del cron. La alternativa más segura es decidir primero la política y, si se aprueba, limitar el retry al tiempo restante y conservar SQS como fallback.
