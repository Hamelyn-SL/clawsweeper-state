## Summary

Mantener abierta: `getOrder` aún realiza una sola llamada ante `500`, aunque el cron conserva el mensaje para reintento SQS; falta decidir una política acotada que no agrave el presupuesto de 150 segundos.

## What This Changes

La incidencia pide manejar de forma segura los `500` transitorios de Amazon SP-API `getOrder` durante `amazon-notifications-pull`.

## Best Possible Solution

Definir un retry HTTP breve y consciente del presupuesto para `getOrder`, conservando la reentrega SQS como salvaguarda y validándolo contra cargas lentas de notificaciones.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Debe `getOrder` hacer un retry HTTP acotado dentro de cada mensaje, o mantenerse exclusivamente la reentrega SQS ante `500` de Amazon?

Rationale: Ambas opciones preservan mensajes, pero cambian la latencia, el número de llamadas al proveedor y el riesgo de alcanzar el límite del cron.

Likely owner: HamelynDev

Owner reason: Introdujo el patrón de retry Amazon actualmente fusionado y puede valorar su extensión a `getOrder`.

Owner confidence: medium

Options:

- **Retry acotado con presupuesto (recommended):** Reutilizar `withHttpRetry` con pocos intentos y un límite compatible con el presupuesto restante del cron.
- **Solo reentrega SQS:** Mantener una única llamada por ejecución y delegar todos los `500` transitorios a la siguiente entrega de SQS.

## Reproduction Assessment

No hay una reproducción live reciente de alta confianza. El código confirma que un `500` de `getOrder` llega al `catch` y deja el mensaje para reentrega SQS.

## Solution Assessment

No concluyente: el helper compartido ofrece una vía mantenible, pero su política debe respetar el presupuesto del cron antes de aplicarse.
