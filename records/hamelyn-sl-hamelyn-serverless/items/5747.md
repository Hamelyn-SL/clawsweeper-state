## Summary

Keep open: current dev still routes `OrderStatusChange`/`Unshipped` notifications through `getOrder`, and that call is not using the bounded HTTP retry path that already exists for `searchOrders`; the current SQS handling prevents deletion on failure, but it does not resolve the live provider 500s.

## What This Changes

The issue requests handling production Amazon SP-API `getOrder` 500s during `/api/amazon-notifications-pull` order-change notification processing.

## Best Possible Solution

Confirm current live frequency by Amazon marketplace, then either add a bounded `Retry-After`-aware `getOrder` retry/backoff path that preserves SQS retention or keep this as an Amazon SP-API support escalation.
