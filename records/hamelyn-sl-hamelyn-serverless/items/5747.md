## Label Justifications

- `P1`: El flujo de notificaciones de pedidos Amazon puede retrasarse repetidamente cuando el proveedor devuelve 500.
- `impact:other`: La afectación es operativa sobre el procesamiento de pedidos, mientras SQS conserva los mensajes no completados.

## Summary

Mantener abierta: el código conserva el mensaje SQS cuando `getOrder` falla, pero no clasifica ni limita un reintento para `500` de SP-API; la política debe equilibrar recuperación y presupuesto del cron.

## What This Changes

La incidencia solicita decidir cómo tratar los errores `500` de Amazon SP-API `getOrder` durante el pull de notificaciones de pedidos.

## Best Possible Solution

Conservar la reentrega SQS como base y, si se confirma recurrencia, añadir solo un retry acotado para errores SP-API 5xx con backoff, presupuesto compartido y métricas de reintentos.

## Maintainer Decision

Rationale: La elección afecta simultáneamente a cuota de Amazon, latencia del cron y velocidad de recuperación; el código no puede fijar ese equilibrio sin una política operativa.

Likely owner: Miguel Angel Hernández Perdomo

Owner confidence: medium

Options:

- **Mantener solo reentrega SQS (recommended):** Conservar el comportamiento actual y abrir caso con Amazon si reaparecen 5xx sostenidos con evidencias recientes.
- **Añadir retry presupuestado:** Reintentar únicamente 5xx transitorios con un máximo pequeño, backoff y corte antes del presupuesto del cron.

## Reproduction Assessment

No hay una reproducción actual de un `500` de Amazon con alta confianza. El código permite verificar que ese error se propaga y que el mensaje queda retenido para reentrega SQS.

## Solution Assessment

Incierto: un retry local puede ayudar ante fallos breves, pero la reentrega SQS ya protege contra pérdida y el límite correcto requiere una decisión operativa.
