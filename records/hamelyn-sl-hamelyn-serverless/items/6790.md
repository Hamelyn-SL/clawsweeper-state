## Summary

La issue sigue siendo necesaria: `dev` mantiene las mutaciones genéricas que pueden retirar una unidad con motivo `SOLD` sin persistir `soldAt`, mientras que el único PR relacionado se cerró sin merge y no cubría el backfill ni las alternativas.

## What This Changes

Corregir las retiradas de stock vendidas que no rellenan `soldAt`, recuperar los datos históricos vinculables y definir el tratamiento de `SOLD_AS_ALTERNATIVE`.

## Best Possible Solution

Aplicar una corrección acotada para que las retiradas genéricas con `SOLD` resuelvan y persistan el marketplace del pedido cuando exista; después, aprobar la semántica de alternativas y ejecutar un backfill local con dry-run, métricas de cobertura y lotes reintentables.

Likely owner: Alex Cantón

Owner reason: La decisión afecta directamente a los endpoints de admin y picking que activan las retiradas genéricas.

Owner confidence: medium

Options:

- **Heredar el marketplace final (recommended):** Guardar en `soldAt` el marketplace del pedido también para alternativas, de modo que el campo mantenga el canal de venta de la unidad finalmente expedida.
- **Conservar una distinción explícita:** No rellenar `soldAt` para alternativas hasta acordar un campo o criterio separado que preserve la relación de sustitución.

## Reproduction Assessment

Sí, por código: actualizar un stock desde admin con motivo `SOLD` alcanza `withdrawStockById`, que no escribe `soldAt`; la consulta de BigQuery del reporte permite medir el efecto en datos reales.

## Solution Assessment

No como una única intervención: cerrar la ruta `SOLD` es una corrección concreta, pero el backfill histórico y `SOLD_AS_ALTERNATIVE` necesitan una decisión de datos antes de aplicarse.
