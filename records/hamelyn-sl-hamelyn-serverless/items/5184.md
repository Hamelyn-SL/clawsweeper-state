## Label Justifications

- `P1`: La creación de nuevas ofertas de eBay permanece pausada y el problema bloquea la recuperación segura de ese flujo.
- `impact:other`: El impacto comprobado es operativo: listings no creados y una señal de salud insuficiente del cron.

## Summary

Mantener abierta: `ebay.create()` sigue pausado y, al reactivarlo, el cron aún puede devolver HTTP 200 tras rechazos de publicación; falta acordar la señal operativa segura.

## What This Changes

La incidencia solicita que los fallos completos o parciales de `bulkPublishOffer` no queden absorbidos por el cron de eBay.

## Best Possible Solution

Definir qué fallos de publicación degradan o alertan el cron, añadir detalle por oferta y reactivar create solo con una validación real de lotes correctos y rechazados.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Debe `/api/ebay` seguir respondiendo HTTP 200 ante un lote create totalmente rechazado, o debe emitir una señal operativa de fallo antes de reactivar `ebay.create()`?

Rationale: El código puede conservar diagnósticos por SKU, pero la semántica de salud del cron y la recuperación de listings requieren una decisión operativa explícita.

Likely owner: JavierHamelyn

Owner reason: Su corrección fusionada controla la propagación actual de errores por SKU y es la base técnica de una reactivación segura.

Owner confidence: high

Options:

- **Exigir señal de fallo antes de reactivar (recommended):** Mantener create pausado hasta registrar el detalle por oferta y acordar una alerta o estado de ejecución para lotes totalmente rechazados.
- **Reactivar con HTTP 200 parcial:** Conservar el contrato actual y asumir que `stocksOnError` y los logs son suficientes para la operación diaria.
- **Distinguir fallo total y parcial:** Mantener HTTP 200 para rechazos aislados, pero degradar o alertar cuando una fase create no publica ninguna oferta.

## Reproduction Assessment

No en producción actual: `ebay.create()` está deshabilitado. Sí hay una ruta reproducible desde código al reactivarlo, donde `bulkPublishOffer` conserva rechazos parciales y el handler responde 200.

## Solution Assessment

No del todo: preservar errores por SKU es correcto, pero reactivar create sin definir la señal para fallos totales mantendría la ambigüedad operativa.
