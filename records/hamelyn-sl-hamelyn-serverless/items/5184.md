## Label Justifications

- `P1`: La creación de nuevas ofertas de eBay permanece desactivada como mitigación de un fallo recurrente de producción.
- `impact:other`: El problema impide publicar nuevas ofertas y degrada la observabilidad operativa de la sincronización de eBay.

## Summary

Mantener abierta: `dev` sigue sin ejecutar `ebay.create()` y conserva tanto la aceptación de respuestas fallidas de `bulkPublishOffer` como el HTTP `200` del cron degradado. Las correcciones posteriores clasificaron causas concretas, pero no reactivaron la publicación ni resolvieron su señal operativa.

## What This Changes

La incidencia pide conservar detalle accionable de los rechazos de `bulkPublishOffer` y evitar que los lotes de publicación fallidos aparenten una ejecución sana del cron de eBay.

## Best Possible Solution

Reparar aquí el contrato específico de `bulkPublishOffer`: conservar errores estructurados por `offerId` y SKU, elevar inequívocamente los lotes con cero éxitos y reactivar create solo después de una ejecución controlada; la política HTTP compartida debe resolverse en https://github.com/Hamelyn-SL/hamelyn-serverless/issues/5622.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Qué condición operativa debe permitir reactivar `ebay.create()`: rechazar la fase cuando un lote tenga cero publicaciones correctas, emitir una alerta estructurada manteniendo HTTP `200`, o exigir ambas señales?

Rationale: La mitigación temporal continúa activa y el código no define qué severidad, respuesta o evidencia real hacen segura la reactivación; esa elección afecta alertas, reintentos y operación del marketplace.

Likely owner: JavierHamelyn

Owner reason: Combina el historial más amplio en la implementación actual de eBay con la autoría del seguimiento sobre la política transversal del cron-handler.

Owner confidence: high

Options:

- **Fallar lotes sin éxitos (recommended):** Rechazar la fase create cuando `successfulPublications === 0`, conservar los errores individuales y reactivarla tras una prueba controlada.
- **Alertar sin rechazar:** Mantener la fase resuelta y HTTP `200`, pero emitir una incidencia estructurada de severidad alta para cada lote completamente fallido.
- **Esperar la política global:** Mantener create desactivado hasta que https://github.com/Hamelyn-SL/hamelyn-serverless/issues/5622 establezca la semántica compartida de los crons degradados.

## Reproduction Assessment

Sí, con confianza alta a nivel de fuente: los rechazos de `bulkPublishOffer` se convierten en errores de stock, el handler común mantiene HTTP `200` y la fase create está desactivada desde el 2 de junio de 2026. No existe una reproducción viva ordinaria desde el cron mientras esa fase continúe comentada.

## Solution Assessment

No: la desactivación temporal evita repetir la incidencia, pero también elimina la publicación de nuevas ofertas. La solución más mantenible es corregir y probar el contrato específico de publicación, coordinando por separado la política HTTP global.
